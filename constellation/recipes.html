A. Create, consult, and inspect without effects

Runnable This credential-free route creates actual local Plan Core state, then shows how an external caller consults AG-hosted Phosphor independently. It contacts no model and performs no planned work.

git clone https://github.com/unpingable/maude.git
cd maude
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
mkdir -p /tmp/constellation-plan-example
.venv/bin/maude-plan --store /tmp/constellation-plan-example/plans.sqlite new \
  --draft-id integration-example --goal 'inspect a local service plan' --workspace "$PWD"
.venv/bin/maude-plan --store /tmp/constellation-plan-example/plans.sqlite check integration-example
.venv/bin/maude-plan --store /tmp/constellation-plan-example/plans.sqlite inspect integration-example
.venv/bin/maude-plan --store /tmp/constellation-plan-example/plans.sqlite lock integration-example

These commands create user-owned plan state and return exact revision/check/lock records. A lock binds bytes; it does not authorize or execute the plan. The caller owns the store and may remove /tmp/constellation-plan-example after retaining anything needed. Maude’s optional design demo is a separate authoring UI with a deterministic corpus; it is not the AG-hosted Phosphor component.

Adapt an external read-only caller

For AG-owned campaign records, start Phosphor’s deterministic demo as described in the public operator guide, then run the small Python reader from this site:

python3 examples/read_phosphor.py \
  --url http://127.0.0.1:8417/api/v1/campaigns

The reader accepts only loopback HTTP, issues one GET, bounds the response, requires the exact campaign-index schema, and reports each owner source as available or unavailable. It deliberately does not collapse those fields into a health, freshness, readiness, or authorization verdict. The Maude plan above is not inserted into this demo: the two steps demonstrate separate public interfaces. If a source is unavailable, preserve that absence, inspect the configured owner and original store, and resume read-only consultation after repair; do not synthesize a value or alter the record. Use semantic detail links returned by Phosphor rather than treating the opaque locator token as campaign identity.

B. Governed bounded action

Incomplete public recipe The public source exposes AG’s authorization machinery and Docket’s execution-custody machinery, but this site does not yet have a public-only, end-to-end disposable action package with the required standing inputs, exact-work issuance, executor, refusal case, and uncertain-outcome recovery case. The following command is a supporting developer check, not Recipe B completion:

git clone https://github.com/unpingable/constellation-docket.git
cd constellation-docket
git checkout c49ad8d0f26fb2a13b9dbafdde84d7abfe1f867b
cargo test --locked -p gwr-local executor_transport

The test harness supplies local plans, attempts, markers, executor responses, and negative controls. Those are substitutions for a caller’s real standing, authorization, and executor. The command validates the published transport behavior at the pinned revision; it does not grant authority or establish that a different executor is safe to run. Read the transport contract before implementing an adapter.

Caller boundary: a deployment must provide its own authorized exact work, standing resolver, executor program/configuration, exclusive target custody, and recovery evidence. Docket retains the attempt; the executor remains responsible for its effect-specific idempotency and reconciliation.

A complete Recipe B must additionally demonstrate one bounded action, a refusal before execution, and an uncertain result reconciled through the same attempt without redispatch. The current public cache kit cannot fill that role because its connected path depends on Pulse material that is not publicly distributed. Synthetic standing or NQ fixtures may test a named boundary, but they cannot be relabeled as the actual AG or Docket services.

C. Connected disposable cache

Not publicly runnable The intended order is host observation and Pulse support → Maude plan → Nightshift proposal → AG authorization → Docket execution and settlement → owner NQ result check → separately governed teardown. This is not a copy-and-paste public recipe yet.

external observation → Pulse support → Maude locked plan
        → Nightshift proposal → AG one-use decision
        → Docket attempt → executor outcome → settlement
        → owner NQ result check → separate teardown decision

Local development qualification has exercised a bounded cache occurrence and governed teardown, but that does not supply a public installation route. The public path still depends on a compatible Pulse distribution and a complete, reviewed connected tutorial/recovery package. A later development attempt also required manual recovery work, so it is not presented here as a successful newcomer route. Private Monitor source and campaign records are deliberately not linked or reproduced.

Until those dependencies are published and the public-only route is independently repeated, use Recipe A for authoring/inspection and the command under B only as a Docket transport developer check. Do not assemble C from repository heads or reuse an old occurrence. The selected Docker daemon is a deployment trust boundary; image digest, storage limits, an exclusive project name, attempt reconciliation, and separately authorized teardown must all be explicit.

Choosing safely

  • If you need to understand plans or adapt a read-only caller, use A.
  • If you are implementing an executor boundary, use the supporting Docket check under B, while treating B itself as incomplete.
  • If you need the complete cache workflow, C is a tracked integration target rather than a supported public recipe.
