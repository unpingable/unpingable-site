A. Read-only authoring and inspection

Runnable This credential-free route uses public Maude source and a deterministic local corpus. It contacts no model and performs no planned work.

git clone https://github.com/unpingable/maude.git
cd maude
PHOSPHOR_DESIGN_PORT=28427 \
  scripts/run-phosphor-design-demo.sh /tmp/maude-authoring-walkthrough

Open http://127.0.0.1:28427/phosphor/design. The caller chooses an unused loopback port and a disposable output directory, then owns stopping the foreground process and removing that directory. Follow the bounded authoring walkthrough. The corpus contains substitutions; it is not evidence of a connected run.

B. Governed executor transport in a disposable fixture

Runnable development fixture Docket’s public conformance case exercises its governed-executor transport and local custody rules without requiring a provider credential or an application deployment.

git clone https://github.com/unpingable/constellation-docket.git
cd constellation-docket
git checkout c49ad8d0f26fb2a13b9dbafdde84d7abfe1f867b
cargo test --locked -p gwr-local executor_transport

The test harness supplies local plans, attempts, markers, executor responses, and negative controls. Those are substitutions for a caller’s real standing, authorization, and executor. The command validates the published transport behavior at the pinned revision; it does not grant authority or establish that a different executor is safe to run. Read the transport contract before implementing an adapter.

Caller boundary: a deployment must provide its own authorized exact work, standing resolver, executor program/configuration, exclusive target custody, and recovery evidence. Docket retains the attempt; the executor remains responsible for its effect-specific idempotency and reconciliation.

C. Connected disposable cache

Not publicly runnable The intended order is host observation and Pulse support → Maude plan → Nightshift proposal → AG authorization → Docket execution and settlement → owner NQ result check → separately governed teardown. This is not a copy-and-paste public recipe yet.

Local development qualification has exercised a bounded cache occurrence and governed teardown, but that does not supply a public installation route. The public path still depends on a compatible Pulse distribution and a complete, reviewed connected tutorial/recovery package. A later development attempt also required manual recovery work, so it is not presented here as a successful newcomer route. Private Monitor source and campaign records are deliberately not linked or reproduced.

Until those dependencies are published and the public-only route is independently repeated, use Recipe A for authoring/inspection and Recipe B for the Docket transport contract. Do not assemble C from repository heads or reuse an old occurrence. The selected Docker daemon is a deployment trust boundary; image digest, storage limits, an exclusive project name, attempt reconciliation, and separately authorized teardown must all be explicit.

Choosing safely

  • If you need to understand plans, use A.
  • If you are implementing an executor boundary, use B and its conformance corpus.
  • If you need the complete cache workflow, C is a tracked integration target rather than a supported public recipe.
