A. Consult a local plan before answering

Profile: maude-plan-consultation/v1. An external caller asks Maude for the selected draft's recorded revision and check/lock summary. This credential-free profile uses real caller-created local state, not a substituted owner response. It starts no service and does not validate, accept, authorize, or execute the proposed work.

Run the versioned public-source example for exact prerequisites, source pins, setup, inspection, refusal and recovery instructions. The frozen manifest lists the tested composition; the qualification record separates clean reproduction from component negative controls. Tag publication is recorded on the guide.

your caller → bounded reader → Maude CLI --read-only inspect → your plan store
your caller ← available revision / unavailable reason ← Maude owner projection

The external boundary is the supplied reader, not direct database access or a new SDK. Its ten-second deadline, one-MiB stream limits, schema checks and no-automatic-retry behavior bound the consultation. Inspect availability in its JSON: an unavailable response also exits zero. Keep writers quiescent for a consistent aggregate; record identity does not establish current external conditions or legitimate reliance.

Separate inspection demo, outside this profile

AG-hosted Phosphor offers an independent deterministic display corpus and bounded loopback HTTP reader. Its public-source component demonstration reproduced the generated corpus, an honestly unavailable owner source, owned-server loss, and byte-identical same-corpus recovery. It does not read this Maude store and is not part of the released Maude profile. The display corpus is a fixture, not live state or legitimate reliance.

B. Governed bounded action

Incomplete public recipe The public source exposes AG’s authorization machinery and Docket’s execution-custody machinery, but this site does not yet have a public-only, end-to-end disposable action package with the required standing inputs, exact-work issuance, executor, refusal case, and uncertain-outcome recovery case. The following command is a supporting developer check, not Recipe B completion:

git clone https://github.com/unpingable/constellation-docket.git
cd constellation-docket
git checkout c49ad8d0f26fb2a13b9dbafdde84d7abfe1f867b
cargo test --locked -p gwr-local executor_transport

The test harness supplies local plans, attempts, markers, executor responses, and negative controls. Those are substitutions for a caller’s real standing, authorization, and executor. The command validates the published transport behavior at the pinned revision; it does not grant authority or establish that a different executor is safe to run. Read the transport contract before implementing an adapter.

Caller boundary: a deployment must provide its own authorized exact work, standing resolver, executor program/configuration, exclusive target custody, and recovery evidence. Docket retains the attempt; the executor remains responsible for its effect-specific idempotency and reconciliation.

A complete Recipe B must additionally demonstrate one bounded action, a refusal before execution, and an uncertain result reconciled through the same attempt without redispatch. The public Pulse NQ host-load support cut supplies one prerequisite, not the missing reviewed action package, standing inputs, or recovery qualification. Synthetic standing or NQ fixtures may test a named boundary, but they cannot be relabeled as the actual AG or Docket services.

C. Connected disposable cache

Not publicly runnable The intended order is host observation and Pulse support → Maude plan → Nightshift proposal → AG authorization → Docket execution and settlement → owner NQ result check → separately governed teardown. This is not a copy-and-paste public recipe yet.

external observation → Pulse support → Maude locked plan
        → Nightshift proposal → AG one-use decision
        → Docket attempt → executor outcome → settlement
        → owner NQ result check → separate teardown decision

Local development qualification has exercised a bounded cache occurrence and governed teardown, but that does not supply a public installation route. The compatible Pulse adapter is now public and component-qualified; the complete reviewed connected tutorial, standing enrollment, and recovery package are still missing. A later development attempt also required manual recovery work, so it is not presented here as a successful newcomer route. Private Monitor source and campaign records are deliberately not linked or reproduced.

Until those dependencies are published and the public-only route is independently repeated, use Recipe A for authoring/inspection and the command under B only as a Docket transport developer check. Do not assemble C from repository heads or reuse an old occurrence. The selected Docker daemon is a deployment trust boundary; image digest, storage limits, an exclusive project name, attempt reconciliation, and separately authorized teardown must all be explicit.

Choosing safely

  • If you need to understand plans or adapt a read-only caller, use A.
  • If you are implementing an executor boundary, use the supporting Docket check under B, while treating B itself as incomplete.
  • If you need the complete cache workflow, C is a tracked integration target rather than a supported public recipe.
