## Participant, materials and conduct

Recruit one competent Linux operator with no Constellation experience. Give the operator only the combined candidate release page, source-free release artifacts, Workbench and the installed/published operator documentation. No source checkout, Cartography archaeology, architecture lecture, unpublished commands, source snippets, agent rescue or silent agent repair is available to the participant. Instructions and inspection examples below must enter the actual operator documentation before the run; this supervisor document is not a substitute for product documentation.

Workbench is the primary surface. The release page may document a CLI escape path for genuinely unsupported Workbench operations, diagnosis or recovery. Record every fallback and whether the documentation made it discoverable. The observer may protect the admitted boundary or stop the run, but cannot supply missing architecture knowledge. Needing unpublished architecture knowledge is a product/documentation defect, even when the underlying component works.

Use an admitted fresh local Ubuntu 22.04 system with a deliberately safe user canary. No important production service, NAS/Plex workload or real operational incident is degraded. Default remediation is deterministic v1; the qualified model mode is optional and requires its separate enrolled accounting/provider/disclosure authority. Human qualification does not silently enable it. Notifications remain local-only until an explicit separate authorization enrolls the dedicated TEST PagerDuty route. No qualification notification goes to production PagerDuty, Slack or other human routes. Lack of effect authority is a normal reported state, not permission to create it.

This document launches nothing. Before execution, root must admit the exact resource/storage envelope and approved durable execution/evidence mechanism and persist the run checkpoint. Reconcile an interrupted original producer before restarting anything. The operator must receive the final source-free documents, not references to local campaign paths.

## Five scores and defect handling

Assign exactly one score to each of the 12 tasks, using the highest assistance needed. A documented CLI escape can still score obvious if it was plainly exposed by the product instructions; separately record the fallback for Workbench integration review.

| Score | Definition |
|---|---|
| **obvious** | Completed using the presented surface/instructions without rereading or searching. |
| **needed rereading** | Completed after rereading the immediately supplied instructions or surface text. |
| **needed documentation search** | Completed only after searching the supplied operator documentation/release page; record pages and search terms. |
| **needed human hint** | Needed a verbal/private hint or unpublished architecture/command knowledge. This is a product/documentation defect; do not erase it by coaching. |
| **blocked** | Could not complete using the allowed materials, or the required release capability/artifact/documentation was absent. Record the blocking condition and stop dependent unsafe work. |

There is no invented numerical pass threshold. Preserve the 12-task score vector and all defects for independent combined-release acceptance. Any human hint, block, false identity/currentness/recovery claim, unexplained authority increase or wrong notification route prevents a clean operability claim until independently reviewed. An agent fixing the system invalidates the affected attempt; preserve it and use a new admitted run identity for any later successor. Do not overwrite a failed occurrence or turn a coached second try into the original pass.

## Documented CLI escape: source-verified inspection examples

These are command shapes verified from accepted source. The integrated package's `--help` and installed manual must be checked and frozen before handing them to the operator. ```sh

```sh
ag-loopctl inspect --database "<AG_DATABASE>"
ag-loopctl status --database "<AG_DATABASE>"
ag-loopctl replay --database "<AG_DATABASE>"

printf '%s\n' '{"v":1,"cmd":"inspect","reservation_id":null}' | la_inference --store "<LA_EXISTING_BOOK>" inspect
la_inference --store "<LA_EXISTING_BOOK>" reconcile --milestone "<MILESTONE_ID>"
```

AG inspect returns current occurrence, replay and runtime-profile binding and checks current/replay digest agreement. History and refusals explain durable progression and nonauthorizing refusals. These commands do not advance the engine, but their SQLite open is READ_WRITE and may configure sidecars; execute under the documented state-access principal against the exact existing database. Do not advertise arbitrary unprivileged SQL access.

Docket governed-loop inspect reads one exact existing issuance custody record, SQLite READ_ONLY/NOFOLLOW, without initialization, resolver or executor. The operator must obtain the issuance locator through the product's ordinary status/outcome view. Do not guess one. Generic Docket root help mentions initialization for stateful commands, but this exact inspector requires an existing store. Docket has no source-defined `--version` command: identify its exact release using installed package metadata and the executable hash manifest instead.

LA version identifies crate/protocol/schema, not the whole release. Inspect/reconcile make no inference debit, but take the writer lock and may create lock/WAL or initialize an absent book; use an existing named production book with the documented root access. Do not substitute `--dev`, relocate/copy the books or invent a new store for an inspection. Reconcile all relevant enrolled milestone IDs; require structured verdict, not just exit zero. No provider call is needed for inspection.

For retained consumer pass outcomes, the final operator document may use:

```sh
journalctl --unit "<CONSUMER_UNIT>" --since "<SCENARIO_START_RFC3339>" --output cat --no-pager
```

This is an OS journal inspection shape, not proof that a particular future unit/outcome projection exists. The release owner must fill the actual unit and expose a bounded secret-free outcome view. The source-defined consumer emits a one-line JSON pass/result/episode summary; exit zero can mean acted, abstained, refused, escalated, pending or busy. A stored consumer result or successful Docket receipt alone does not prove recovery: the operator must find a fresh qualified postcondition/current observation and the corresponding AG final state. Keep unknown, failed and indeterminate outcomes visible.

The consumer's normal `--config` invocation runs a pass and may act; it is not a status command. Its `--check-config` validates configuration only and says nothing about recovery. Never invoke `docket-standing-grant-resolver` as a read-only probe: it consumes grant use. Do not use AG advance/proposal/effect commands, Docket reconcile/dispatch or LA recover/settle/enroll as inspection substitutes. Any mutating recovery task must use its separately documented supported workflow and enrolled authority.

Source identity alone does not verify installed identity.
