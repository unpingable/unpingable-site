# Operate the short supervised trial

On the primary path, run commands from `/opt/constellation-try/constellation-canonical-candidate-20261010`. On the manual study path, use the verified extracted directory supplied to enrollment. Choose one unit/path; do not enroll both on one VM. Read [Known issues](KNOWN-ISSUES.md): the persisted envelope can refuse further writes when capacity or protected history prevents safe admission, and AG's `completed` state is not the result of the Start. Plan a supervised session of up to four hours and end it the same day; nothing here claims unattended operation.

Enter through Workbench `/operator.html`; inspect its plan at `/plan.html`. The current native sources, raw provenance, gaps, attempts and refusal reasons are available alongside the interpretation. Workbench's `READ_OK` means the source binding/schema read succeeded. It does not mean every unit, host, dependency or application is healthy.

`current` supports the named native proposition within its enrolled identity and time boundary. `contradictory` describes evidence contradicting that proposition. `stale`, `absent`, `unsupported`, `refused` and unavailable reads remain explicit; browser refresh does not collect or refresh evidence. Newest unsupported evidence cannot be replaced by an older passing row. Boot identity, observation time, evaluation time and presentation time are distinct. Diagnosis and diagnostic-depth selection grant no effects.

The installed Workbench pages are **read-only**. The separate `constellation-live-reader.service` implements the native reader/action facade: it checks request/enrollment state and invokes AG; AG remains authoritative for governed transitions. Governed recovery uses the separate native API on port 8081 (`http://127.0.0.1:8081`) through the documented CLI escape. The API selects fixed enrolled plans and never accepts a caller command or new target. Its GET reads (`/api/read`, `/api/attempt`, `/api/enrollment`) need no credential; POST `/api/actions` requires the operator token the helper reads from `/var/lib/constellation-live-ecad/private/operator-token`, hence `sudo`. The API binds all guest interfaces. Both documented first-run paths require the loopback restriction in [Installation](INSTALLATION.md); GET reads remain unauthenticated even when access is confined. Workbench on 127.0.0.1:18861 is only the read-only page and does not serve `/api/attempt`. On the primary nginx trial, first stop only the enrolled unit, then wait for current native inactive evidence:

```sh
sudo systemctl stop nginx.service
```

The manual study instead stops only `constellation-beta-http-fixture.service`. For fresh evidence explicitly reporting a failed unit, `prepare` also supports `--prestate failed`; match the actual enrolled unit state, do not manufacture a failure. The example below uses inactive evidence:

```sh
sudo python3 scripts/native-action.py prepare --identity operator-cli --prestate inactive --assessment 'Current native evidence shows the enrolled unit inactive; cause is not established.'
sudo python3 scripts/native-action.py init
sudo python3 scripts/native-action.py record-proposal
sudo python3 scripts/native-action.py require-standing
sudo python3 scripts/native-action.py decide
sudo python3 scripts/native-action.py authorize
sudo python3 scripts/native-action.py dispatch
sudo python3 scripts/native-action.py poll
```

`--identity` (required by `prepare`, no default) is recorded as the worker identity in the attempt; name whoever actually drives it: `operator-cli` above stands for a person at the command line, and an agent-driven run must pass something like `agent-preflight`.

Inspect every native result. A successful HTTP response is not completion. Never repeat an uncertain dispatch. `OBSERVATION_CHANGED` during preparation means acquire fresh context for a new non-authorizing preparation only if no attempt was created. Later refusals preserve the existing attempt; inspect `/api/attempt` and reconcile before any recovery operation. No automatic retry is supplied by these helpers. If `authorize`, `dispatch` or `poll` was interrupted (crash, reboot, timeout), run `sudo python3 scripts/native-action.py recover` instead of repeating it: it maps to `ag-loopctl recover`, which only reconciles the existing authorization or Docket attempt and never creates new authority or a new dispatch. In any other state it reports what fresh revalidation is required.

After exact settlement, explicitly continue into an authority-empty successor and independently wait for fresh current active-unit evidence, including the reader/action facade’s `CURRENT_POSTCONDITION_REQUIRED` precheck and AG’s authoritative postcondition validation. `completed` means the enrolled unit is observed active again in this boot. It says nothing about the application the unit runs, and it does not by itself mean the governed Start succeeded: AG's `complete` does not read the settlement outcome. Read the settlement sentence on the Workbench attempt line, or the settlement record itself, for the result of the Start ([known issues](KNOWN-ISSUES.md)).

```sh
sudo python3 scripts/native-action.py continue
sudo python3 scripts/native-action.py complete
```

`CURRENT_POSTCONDITION_REQUIRED` from `complete` means no current observation of the enrolled unit active exists; do not relax time bounds or force success. Waiting and repeating `complete` helps only while the unit is becoming active after a Start (see [below](#refusals-expiry-and-second-attempts)). Inspect the original and successor occurrences, native AG result and Docket custody. The package includes `ag-loopctl` inspection and Docket's installed enrollment/inspection manual as CLI escape hatches. On the local exercise the AG database is `/var/lib/constellation-live-ecad/ag/campaign.sqlite`: `sudo ag-loopctl inspect --database /var/lib/constellation-live-ecad/ag/campaign.sqlite` shows the current occurrence and replay counts, and `sudo ag-loopctl history --database …` the full transition journal. After `continue`, the current occurrence is the successor; its `history` fields (`settlement`, `receipt`, `ag_spend`, `docket_attempt`) are `null` because it never held authority. The settlement belongs to the original occurrence: see `settlement_recorded` in `history` or `settlements: 1` in `inspect` replay. Do not invoke standing-grant resolvers as read-only probes.

## Refusals, expiry and second attempts

One prepared attempt per enrollment is enforced by the native reader/action facade (`ATTEMPT_ALREADY_EXISTS`, `CAMPAIGN_ALREADY_EXISTS`) and native AG transition checks. Observed second-attempt refusals do not demonstrate that Docket's separate one-use grant limit was reached. A completed attempt does not reopen the grant; do not re-enroll to obtain another governed Start on the same VM. On qualification guests of this package set (an earlier assembly of this candidate with the same packages and scripts), one for each path, with the unit stopped again after a completed attempt, each of the ten steps was refused with exit 2: `prepare` with `ATTEMPT_ALREADY_EXISTS`, `init` with `CAMPAIGN_ALREADY_EXISTS`, `record-proposal`, `require-standing`, `decide`, `authorize`, `dispatch`, `poll` and `continue` with `NATIVE_COMMAND_REFUSED:ag-loopctl`, and `complete` with `CURRENT_POSTCONDITION_REQUIRED`; `recover` answered exit 0 with `external_revalidation`. No start ran, the unit stayed inactive and the grant still showed one use. AG's own reason for the `NATIVE_COMMAND_REFUSED:ag-loopctl` answers was not found in the records: on the manual path `ag-loopctl refusals` returned an empty list, and on the try path the refusal list in `/api/attempt` stayed empty. All such guests were agent-driven lab runs, not human evidence. Runs on the exact archive are recorded in `QUALIFICATION.json` beside the archive.

The grant expires two hours after enrollment. Its resolver refuses new standing derivation with `execution-standing-grant-expired`; the API may report only `NATIVE_COMMAND_REFUSED:ag-loopctl`, so inspect the native records. Expiry does not stop collection, undo a dispatched Start, cancel an existing attempt or erase state. If it expires before authorization, end the session rather than renew it by re-enrollment. For an existing uncertain attempt use the documented `recover`; unresolved results require review, not redispatch.

`CURRENT_POSTCONDITION_REQUIRED` is the facade's answer to `complete` when no current observation of the enrolled unit active exists. Repeating `complete` helps in one situation only: after a Start, while you wait for a real fresh active observation; then repeat `complete` and nothing else. On an attempt that is already completed, with the unit inactive, the same answer is the expected refusal and repeating it does nothing: on the qualification guests of this package set it left AG's record, the grant use and the unit unchanged. The wait-and-repeat case was not exercised there (the first `complete` succeeded each time), and what `complete` answers on a completed attempt once the unit is active again was not tried. If observation remains stale or unavailable, inspect collector evidence (`journalctl -u nqd-ops`); an empty gaps list does not make it current, and a store at its capacity ceiling shows exactly this ([known issues](KNOWN-ISSUES.md)). If recovery cannot be reconciled from the supplied records, stop the trial and preserve them; [Day two](DAY-TWO-RUNBOOK.md) explains withdrawal and a separately admitted fresh VM.

These documents give no command that shows NQ's persisted capacity envelope or its latest report sequence. On the try-path qualification guest of this package set `status export` and `doctor`, each run once through the packaged `nq-ops-as-nq` wrapper, printed no envelope fields (the `status export` output did carry `max_report_sequence`); that single run is not a documented procedure. The installed NQ guide (`/usr/share/doc/nq-ng/OPERATIONS.md`) describes `nqd.service` and its paths, not the `nqd-ops` instance this candidate runs, and names no such command either ([known issues](KNOWN-ISSUES.md#nq-bounded-retention-with-a-finite-ceiling-issue-27-remains-open)).

If you copy the NQ store, stop `nqd-ops` first and copy `nq.db`, `nq.db-wal` and `nq.db-shm` from `/var/lib/nq-ops` together. A graceful stop leaves the `-wal` file in place, and `nq.db` alone can lack the most recent commits ([known issues](KNOWN-ISSUES.md#nq-bounded-retention-with-a-finite-ceiling-issue-27-remains-open)).

## Read the Workbench fields

- **Currentness** shows the Monitor judgment status for the claim "the unit is active in this boot", not data age. `contradictory` (`current_boot_claim_contradicted`) means fresh, current-boot evidence shows the unit is not active. Evidence past its age bound shows as `stale` (`source_or_evaluation_expired`) instead; the native age boundary is 60 seconds, so after stopping the collector expect `stale` once a minute has passed.
- NQ condition `systemd_unit_not_active` with `state: explicitly_absent` means current evidence positively shows the problem condition is absent: the unit is active. `present` means the unit is not active; `cannot_evaluate` means the evidence is insufficient either way.
- **Attempt line** (under the status line, once an attempt exists) reads `Remediation attempt: AG state <state>.` followed by exactly one settlement sentence taken from AG's settlement record: `Governed Start settled as success, <time>.`; `Governed Start settled as FAILURE, <time>: the governed Start did not succeed.`; `No settlement recorded: the governed Start has not been settled.`; `Settlement outcome not readable from the retained AG records; nothing inferred.`; `Settlement records disagree or are unreadable; nothing inferred.`; or, for a summary written without a settlement field, `Settlement outcome is not available in this record; nothing inferred.` `No settlement recorded: the governed Start has not been settled.` describes AG's record only. Between `dispatch` and `poll` the executor and Docket may already have run and settled the Start; AG learns the settlement at `poll`. On the qualification guests of this package set the page still showed this sentence after `dispatch` while the unit was already active (success cases) or Docket had already settled the Start as failure. Run `poll` before reading the result. For `completed` it adds `AG state completed means the unit was observed active after settlement; it does not by itself mean the governed Start succeeded.` Read the settlement sentence, not the state name, as the result of the Start: AG can reach `completed` after a failed settlement ([known issues](KNOWN-ISSUES.md)). The line then gives the boot the attempt was prepared in compared with the host's current boot, and the last action request: the component that answered it or, for a refusal, its reason verbatim. That last part reports the request, not the settlement. It does not record the boot in which the attempt completed, and refusals raised before an action is accepted (credential, framing, schema) appear only to the caller. `FACADE_ATTEMPT_READ_UNAVAILABLE` in the gaps means the attempt summary could not be read.
- **Replay pages** in `/usr/share/constellation-workbench/replay/` (`index.html` links `healthy-cohort.html`, `refusal.html`, `application-relationship.html`, `mixed-version.html` and others) are recorded history, pinned by their replay manifest, not current observation; they show unit state only, not service health, although those four pages do not say so.
- **Native API records** on 8081 (`/api/enrollment` among them) carry no "unit state only" disclaimer; they are unit evidence only, like the pages.
- **Missing instrumentation / owner gaps** (the retained UI label for assertions from components) lists only native read failures in this release: the unit reader refused (`NATIVE_READ_UNAVAILABLE`) or AG inspect refused (`NATIVE_ATTEMPT_READ_UNAVAILABLE`). The plan's gaps add a failed Workbench source read or a missing required observation. HTTP is not a required observation here, and a stopped collector still yields a (stale) observation, so both lists stay `[]` in those cases. An empty list does not mean nothing is uninstrumented.

## Advanced reference

Attention distinguishes informational, attention and page classes. PagerDuty page intent is separate from submission/delivery and from effect authority. Missing input does not establish recovery. The local exercise configures no external notification destination. Reference observation/evaluator/notification/status and optional metrics/Grafana procedures remain in the bundled reference operation and observability manuals. The `reference/` installation path has not been run with this NQ package; do not use it with this candidate ([known issues](KNOWN-ISSUES.md)). Further, this Workbench cohort does not claim to unify those surfaces into one universal health score.

Deterministic remediation v1 is the default of the historical reference path. Its consumer is installed disabled in this candidate: nothing in the try path or the manual path enables it, no automatic remediation has been run on these packages, and every Start here is requested step by step by an operator. Optional v2 uses Linear Accountant to reserve, fence, settle and reconcile inference expenditure; AG/Docket retain authority/custody and fresh observation determines recovery. The Workbench reveal did not exercise LA; a separate remediation-v2 qualification did, on other package bytes, and it is not demonstrated on this candidate. Installation, diagnostic depth, model narration and package presence activate none of that optional authority.

Build inspection: `nq --build-info`, component `--build-info` where documented, `/usr/share/constellation-workbench/build.json`, `dpkg-query`, PACKAGES.json and RUNTIME-IDENTITIES.json. Components without a native build-info command use exact package/executable/source manifests. No fabricated common build endpoint exists.

## Optional inference accounting

Admitted model-backed workflows can disclose the actual LA envelope before
inference and native usage/settlement afterward. Workbench's optional read-only
accounting pane displays selected owner-exported LA assertions. It does not
estimate provider cost or administer budgets. A closed/revoked token's numeric
remaining capacity is retired, not available spending. Unknown actual cost
stays unknown; budget exhaustion offers no continuation action. Accounting is
explicitly recorded and distinct from current evidence/effect authority.

Most Workbench workflows invoke neither a model nor LA.

## Understand monitoring notices

A condition ID is an exact correlation key, not an explanation. `unknown` or `indeterminate` means the available evidence cannot justify a conclusion; `stale` means it is outside the qualified age/boot boundary. "None" means no condition is present in the current observation; it says nothing about application health. A current `clear` applies only to the named proposition. A notification `resolved` closes that condition lifecycle: restored monitoring does not by itself prove the observed service was repaired. Inspect the evidence and scope, then the documented collector/runbook before acting. A page may require prompt human investigation because an obligation cannot be evaluated. Exact IDs remain useful when correlating native records and delivery outcomes.
